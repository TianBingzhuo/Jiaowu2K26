# University OS 扩展包 · 功能规格

> **逻辑模块：** F-010～F-014  
> **文档形态：** 五个模块合并维护，避免为长期愿景新增 15 个散文件  
> **基线日期：** 2026-07-22  
> **状态：** 用户已确认纳入产品范围；全部 `pending`，不是完成声明  
> **赛事边界：** 不进入当前 P0；只有正式开赛、P0 稳定且团队有余量时，才可挑选一个最小纵向切片

## 1. 总使命

把 jiaowu2K26 从“学习与选课工具集合”扩展成覆盖学生、教师和学校三端的大学生涯游戏操作系统：学生在同一世界里处理课程、门禁、消费、饮食、科研与校园生活；教师在同一世界里完成教学、科研与晋升准备；学校在同一世界里观察服务、资源与政策的可解释改进空间。

这不是替换 SIS、财务、门禁、支付、医疗、人事或科研管理系统。jiaowu2K26 只做统一体验、授权镜像、解释、模拟、建议和正式入口跳转；权威决定仍留在原系统和责任人手中。

外部事实、UArizona 全校生态、General Balance 分层和支付/身份边界的官方来源统一登记在 [RESEARCH](../../reference/RESEARCH.md#uarizona-全校数字生态与缺口映射)，本规格不复制第二份来源清单。

## 2. 交付与裁剪规则

| 层级 | 允许交付 | 完成口径 |
|---|---|---|
| Vision | 规格、来源、数据合同、边界与界面流程 | 只能称“规划/候选” |
| Slice | 一个角色、一个场景、一个输入到结果的闭环 | 正式开赛后实现，含来源、失败和回退 |
| Domain MVP | 单个 F 模块的核心交易与治理闭环 | 不依赖人工改库，不冒充权威系统 |
| Campus Pilot | 经学校、支付/门禁服务方和法务批准的受控试点 | 真实权限、合规、运维和申诉均通过 |

默认全部停留在 Vision。若 P0 在 36 小时前稳定，团队也只能从所有 P1/P2/Vision 候选中再选一个 Slice；“已经写进路线图”不等于“本届必须做”。

## 3. F-010 Campus Pass & Entitlements（P2 / Vision）

### 使命

把校园身份、门禁、实验室、设备和非货币权益组织成可解释的通行证钱包。系统展示“为什么有权、何时到期、由谁批准、怎样纠错”，不自行签发正式权限，也不把出入记录变成学生画像。

| ID | 功能 | 具体行为与验收口径 | 阶段 |
|---|---|---|---|
| F010-01 | 校园身份关联 | 关联学生/教职工/访客身份与权威来源；体验层不保存原系统密码 | P2 |
| F010-02 | Pass Wallet | 汇总校园卡、移动凭证、访客证和设备资格，逐项显示签发方、范围、期限和状态 | P2 |
| F010-03 | 多载体凭证 | 兼容实体卡、NFC、动态二维码或受支持移动凭证；静态截图不能冒充动态凭证 | Vision |
| F010-04 | 区域与时段权限 | 用角色、地点、时段和用途表达访问范围；默认最小权限 | P2 |
| F010-05 | 学业联动申请 | 根据课程、实验或岗位提出可解释的权限申请建议；必须由权威方批准 | P2 |
| F010-06 | 临时 / 访客 / 陪同权限 | 支持目的、担保人、时限、区域和自动到期；敏感区域需额外审批 | Vision |
| F010-07 | 实验室与设备前置条件 | 展示培训、安全测验、导师批准和预约要求；条件不满足时给正式办理入口 | P2 |
| F010-08 | 申请与审批镜像 | 显示 draft / submitted / reviewing / approved / externally executed / denied / expired / fault / appeal，并标明只是权威系统状态镜像 | P2 |
| F010-09 | 挂失、冻结与恢复 | 提供正式渠道和确认步骤；冻结、撤销、补发均留下审计事件 | P2 |
| F010-10 | 离线验证与新鲜度 | 断网时只接受有期限的受签凭证，明确最后同步时间和不可用范围 | Vision |
| F010-11 | 通行记录自查 | 用户可查看与本人相关的必要记录、用途、保留期和纠错渠道 | Vision |
| F010-12 | 最小追踪与保留 | 不为推荐或排名长期保存精细移动轨迹；超期自动删除或匿名化 | Vision |
| F010-13 | 安全与应急模式 | 应急解锁、封控和人工处置只由正式安全系统执行，体验层只转达权威状态 | Vision |
| F010-14 | 无障碍与人工回退 | 支持无手机、设备没电、残障陪同和人工核验路径，不把手机作为唯一通行条件 | P2 |

## 4. F-011 General Balance & Campus Commerce（P2 / Vision）

### 使命

给学生一个“看起来统一、账务上严格分离”的校园余额中心：General Cash 可自由用于允许的校园场景，政策补助按用途和期限受限，支付宝/微信支付/云闪付/银行卡等只是外部支付通道，模块限额由学生自行分配并用于预算管理。

| ID | 功能 | 具体行为与验收口径 | 阶段 |
|---|---|---|---|
| F011-01 | 统一余额驾驶舱 | 同屏显示可用、冻结、待入账、即将到期和非货币权益，但不把不同法律属性混成一笔钱 | P2 |
| F011-02 | 分账总账 | General Cash、Policy Balance、外部通道交易、模块预算与权益分别记账，可追溯每次变化 | P2 |
| F011-03 | General Cash | 支持学校允许范围内的通用消费、充值、退款和余额结转规则 | Vision |
| F011-04 | Policy Balance | 奖助、餐补、科研或专项补贴记录来源、允许场景、期限、优先级和退回规则 | Vision |
| F011-05 | External Rails | 对接支付宝、微信支付、云闪付、银行卡或 Stripe 等通道；它们是支付工具，不抓取或汇总用户完整外部余额 | Vision |
| F011-06 | 支付工具管理 | 仅保存令牌化引用和必要状态；绑定、解绑、免密与额度必须由通道侧强认证确认 | Vision |
| F011-07 | 充值、退款与争议 | 每笔操作沿 Preview → Confirmed → Provider Pending → Executed → Reconciled 状态机显示责任方、预计时间、手续费和申诉；失败不得静默扣款或重复执行 | Vision |
| F011-08 | 智能支付路由 | 交易前解释将使用哪一资金来源、为什么、剩余多少；用户可在规则允许时调整顺序 | Vision |
| F011-09 | Module Cap 分配 | 学生为 Academic、Dining、Housing、Mobility、Research、Campus Life、Wellness、Opportunity 等模块设预算 | P2 |
| F011-10 | 提醒、软限额与硬限额 | 支持阈值提醒和软限额；硬限额只作用于学生主动选择的可选消费 | P2 |
| F011-11 | 模块目标完成 | “完成”表示预算目标或计划达成，可获非现金徽章和分析；不得形成付费进度或随机奖励 | P2 |
| F011-12 | 场景与商户规则 | 按商户、类别、地点、时间和政策校验可用范围；拒绝时显示具体规则与替代支付方式 | Vision |
| F011-13 | 课程与校务缴费 | 只镜像应缴、已缴和正式入口；强制学费、健康与应急事项不受学生自设硬限额阻断 | Vision |
| F011-14 | 校园消费 | 覆盖食堂、超市、打印、交通、场馆和经批准服务，统一回执但保留原商户信息 | Vision |
| F011-15 | 资助与基本需要 | 将奖助、紧急援助、Basic Needs 资源和资格说明接入，不把经济困难游戏化或公开化 | Vision |
| F011-16 | 非货币权益分离 | 餐次、打印页、实验室时长、场馆次数等进入 Entitlements，不伪装为现金余额 | P2 |
| F011-17 | 账单、回执与导出 | 提供对账单、电子回执、分类统计、纠错和可携带导出；来源及时间清楚 | P2 |
| F011-18 | 风控与合规隔离 | 异常检测、冻结、退款、支付合规和卡数据范围由受控服务处理；AI 不可独立拒付或冻结账户 | Vision |

## 5. F-012 Dining & Wellbeing（P2 / Vision）

### 使命

把官方菜单、价格、过敏原、营养、排队、预算与个人选择整合成可行动的饮食助手，同时向学校提供聚合的需求、浪费和服务优化建议。它不是医疗诊断工具，也不会用“健康分”羞辱学生。

| ID | 功能 | 具体行为与验收口径 | 阶段 |
|---|---|---|---|
| F012-01 | 官方菜单聚合 | 显示餐厅、档口、餐次、日期、来源、更新时间和变更状态 | P2 |
| F012-02 | 价格与供应状态 | 展示价格、售罄、临时关闭和替代项；缓存信息必须标注时间 | P2 |
| F012-03 | 食材与过敏原 | 仅展示餐饮方确认的信息和免责声明；未知项不能由模型猜测 | P2 |
| F012-04 | 营养信息 | 显示口径、份量和来源；不输出疾病诊断或治疗建议 | P2 |
| F012-05 | 自愿饮食偏好 | 学生主动选择口味、宗教、素食、过敏原和目标，可随时关闭或删除 | P2 |
| F012-06 | 预算内食谱建议 | 结合 General Balance 模块预算给出多套可解释选择，不诱导过度节食或消费 | P2 |
| F012-07 | 课表与位置建议 | 在时间、地点、营业状态和无障碍条件内推荐可达方案，并说明冲突与未知 | Vision |
| F012-08 | 餐次与补助状态 | 显示 Meal Plan、餐次、餐补的剩余、期限和限制，不与现金余额混淆 | Vision |
| F012-09 | 排队与拥挤提示 | 使用聚合或官方数据给区间和时间戳；没有数据时不伪造实时热度 | Vision |
| F012-10 | 反馈与投诉闭环 | 针对价格、卫生、服务、过敏原和无障碍提交结构化反馈并查看处理镜像 | Vision |
| F012-11 | 需求预测 | 用匿名聚合数据预测餐次与品类需求，展示不确定性，人工决定备餐 | Vision |
| F012-12 | 浪费优化 | 聚合剩余、退餐与满意度，建议份量和菜单调整；不追踪个人“浪费排名” | Vision |
| F012-13 | 采购与库存建议 | 给运营方可解释的采购/补货建议，保留供应、价格和食品安全约束 | Vision |
| F012-14 | 包容与安全 | 覆盖无障碍、文化/宗教、经济可负担和紧急求助；高风险问题转正式渠道 | P2 |

## 6. F-013 Faculty Success Studio（P2 / Vision）

### 使命

为教师提供同一游戏世界中的 Coach Studio：把教学证据、科研方向、机会、合规、协作和晋升材料变成可核验的赛季计划与档案。系统帮助准备和解释，不替代同行评议、伦理审查、职称评审或人事决定。

| ID | 功能 | 具体行为与验收口径 | 阶段 |
|---|---|---|---|
| F013-01 | 教师档案 | 汇总岗位、教学、科研、服务和个人目标；本人确认后才进入档案 | P2 |
| F013-02 | 成果导入与去重 | 从学校、ORCID/DOI 或手工来源导入并保留出处、版本、归属与重复判断 | Vision |
| F013-03 | 研究方向建模 | 以 Research Quest Tree 由教师主动定义目标、假设、方法、任务、实验、资源、证据和边界；AI 不从敏感或私密数据臆测方向 | P2 |
| F013-04 | 基金与项目建议 | 匹配资助、项目和截止，逐项解释资格、缺口、风险和官方入口 | Vision |
| F013-05 | 合作者与团队发现 | 基于公开/授权专长和双方意愿推荐，避免按名气或敏感属性排序 | Vision |
| F013-06 | 文献、会议与趋势雷达 | 给出来源、时间、检索式与未知项；不把热度当学术价值 | Vision |
| F013-07 | 科研路线 What-if | 在 Quest Tree 上模拟时间、设备、经费、学生、实验依赖和里程碑组合，输出多方案、阻塞、状态及取舍 | Vision |
| F013-08 | 合规与研究治理 | 提醒伦理、数据、利益冲突、出口管制和安全流程，最终判断跳转权威系统 | Vision |
| F013-09 | 课程设计建议 | 根据课程目标、材料和学习证据给可追溯建议，教师逐项审核后采用 | P2 |
| F013-10 | 教学反馈聚合 | 将结构化反馈按样本、时间和课程版本聚合，屏蔽骚扰与未经核验的人格评价 | P2 |
| F013-11 | 课程改进回放 | 对教学/科研改动、实验结果、证据、效果信号、限制和 Next Move 做版本化 Replay，不轻率宣称因果 | Vision |
| F013-12 | 指导与 Office Hours 负荷 | 汇总预约、主题和积压区间，保护学生隐私，不以响应速度单独评价教师 | Vision |
| F013-13 | 晋升标准地图 | 将院系正式标准映射到教学、科研、服务证据，显示版本、适用范围和未知 | Vision |
| F013-14 | 晋升材料与缺口分析 | 生成可编辑材料清单、证据链接和待确认项；不预测“晋升概率” | Vision |
| F013-15 | 人工审核、申诉与更正 | 教师可修正归属、拒绝建议、导出材料并查看谁使用了哪些数据 | P2 |
| F013-16 | 公平与人事红线 | 不自动作出聘任、续聘、薪酬、绩效或晋升决定，不公开教师 OVR/天梯 | P2 |

## 7. F-014 Institutional Front Office（P2 / Vision）

| ID | 功能 | 具体行为与验收口径 | 阶段 |
|---|---|---|---|

| F014-06 | Advising / Case Management | 按 Draft → Pending → Reviewed → Approved/Rejected → Executed → Reconciled 跟踪预约、转介、待办、责任人与时限，并覆盖 Fault/Appeal；学生可见必要状态并可纠错 | Vision |

| F014-09 | 住宿与交通 | 汇总住宿申请、维修、校车、停车、自行车和无障碍出行的状态与建议 | Vision |
| F014-10 | 图书馆、空间与设备 | 搜索座位、房间、实验设备、借用条件、预约和故障状态 | Vision |
| F014-11 | 无障碍与合理便利 | 跟踪本人授权的需求、办理入口和服务状态；不向无关角色披露诊断信息 | Vision |
| F014-12 | 安全与紧急服务 | 将紧急通知、求助和正式安全渠道置顶；不得用赛事动效延误行动 | P2 |
| F014-13 | 职业与校友 | 汇总职业服务、实习、雇主活动、导师和毕业后可携带档案，由本人控制披露 | Vision |
| F014-14 | 科研管理与合规 | 镜像项目、合同、伦理、数据和设施流程；建议不替代正式审批 | Vision |

## 9. 统一体验合同

五个新增模块与 F-001～F-009 必须共同遵守 [DESIGN-SYSTEM](../../engineering/DESIGN-SYSTEM.md)：

1. 同一个全局壳、导航、色彩、字体、卡片几何、图标、动效和声音规则；模块不能自行换肤。
2. 所有任务遵循 `Briefing → Choose → Execute → Replay → Next Move` 的游戏循环。
3. 学生、教师和学校只是同一世界的三种 Role Lens，不是三套风格不同的产品。
4. 游戏名称必须与正式名称并列；支付、门禁、健康、安全和审批的正式状态永远优先。
5. 沉浸、轻量、传统、减少动效模式共享同一信息架构；关闭游戏措辞不等于退回一个粗糙后台。

## 10. 共享数据对象

| 对象 | 最低字段 |
|---|---|
| `IdentityLink` | 主体、角色、权威来源、关联状态、验证时间、到期时间 |
| `Entitlement` | 类型、签发方、允许范围、前置条件、生效/到期、状态、`source_ids` |
| `LedgerEntry` | 账户桶、方向、金额/单位、币种、交易方、用途、时间、关联规则、不可变引用 |
| `BudgetEnvelope` | 模块、周期、目标、提醒阈值、软/硬限额、用户确认、例外规则 |
| `PolicyRule` | 规则版本、适用对象、允许/禁止场景、优先级、有效期、正式来源 |
| `Recommendation` | 目标、候选、理由、证据、未知、风险、替代项、生成/审核状态 |
| `ServiceCase` | 服务类型、权威系统、责任人、状态、时限、本人可见字段、纠错入口 |
| `InstitutionScenario` | 假设、输入版本、约束、方案、受影响群体、权衡、批准状态 |

## 11. 全局不变量

1. External Rails 是支付通道，不是外部账户总余额聚合器。
2. General Cash、Policy Balance、Module Cap 与 Entitlement 账务和界面语义严格分离。
3. 用户硬限额不得阻断紧急健康、安全和学校规定的强制流程。
4. 门禁、支付、录取、成绩、资助、医疗、纪律、人事和晋升的正式决定不能由 AI 或体验层自动作出。
5. 推荐必须给出来源、理由、未知、替代方案和正式下一步；用户可关闭、纠错或拒绝。
6. 机构分析默认使用最小化、聚合或匿名数据，不建立公开个人 OVR、消费榜、通行榜或绩效榜。
7. 游戏化奖励不得购买资格、成绩、优先级或现实权益，不得随机分配稀缺教育机会。
8. 所有模块默认 `pending`；没有现场代码、测试和运行证据时只能称为愿景。
