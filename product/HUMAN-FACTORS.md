# 人因研究章程与游戏机制覆盖审计

> **状态：** 赛前/开工交界期的研究基线；不代表任何功能已经实现或通过用户验证。  
> **更新时间：** 2026-07-23
> **当前责任：** 暂无独立人因队员；Codex 负责可查证预审、协议和分析草案，`product_integrator` 负责审核、真实参与者研究与最终决定。未来志愿者可按能力认领，但不能成为单点依赖。
> **机制事实源：** [NBA 2K × maimai 全功能机制对标](../brainstorm/03-2K全功能对标与实现构思.md)。本文不复制完整转译文案，只负责研究责任、覆盖状态与采用闸门。

## 1. 一眼结论

现有清单共审计 **139 条游戏机制**：

- NBA 2K 部分 94 条，其中 92 条属于 2K25 系统，另有 2 条明确标注为系列参照（`2K24 Mamba Moments`、`All-Star Weekend / awards`）。
- maimai DX 部分 45 条。
- 116 条已经给出“采用 / 改造采用 / 采用语法 / 采用目标”的安全转译，21 条延后，2 条拒绝原机制但保留了明确的安全替代或禁用理由。
- **139/139 都有产品去向：** 134 条落到 F-001～F-014，一个机制可跨多个模块；另 5 条只落到 `01 基座` 或 X-08/X-11/X-13 等共享合同。
- 项目已有 214 个稳定功能 ID，但现有游戏表多数只追到模块级，没有逐条追到 `Fxxx-xx → 页面/接口 → 测试证据`。这属于**追溯缺口**，不是功能缺失。
- **已实现：0/139；已完成人因验证：0/139。** 目前只有规格映射，不能对队友、评委或下一位 AI 说“这些机制已经做进程序”。

## 2. 为什么仍需独立的人因能力

这不是一个“发问卷、算满意度”的边缘工作。jiaowu2K26 同时碰到成绩、机会、师生权力、学校治理、门禁、支付、饮食、科研和人事；游戏机制又会改变用户如何理解成功、失败、身份与公平。人类学训练很适合观察语境、意义、制度权力和群体差异，但项目不能把安全责任绑定到某一位可能离队的同学。

当前采用弹性架构：Codex 可以完成来源核验、规格追溯、风险假设、访谈脚本、匿名材料编码和报告草案；产品总集成人员逐项审核，并亲自组织或委托真人参与研究。AI 模拟、生成式 persona 和模型自问自答永远不能计作用户证据。

`human_factors_research` 这一能力面的职责是：

1. **文化语义：** 检查 2K、舞萌、赛季、温度、徽章、Boss 等隐喻在不同用户中的真实含义，不假设所有人都懂梗。
2. **认知与行动：** 验证用户能否看懂正式状态、来源、限制和下一步，而不是只觉得“很酷”。
3. **压力与身份：** 找出羞辱、焦虑、上瘾、FOMO、完美主义和永久标签风险。
4. **权力与公平：** 研究学生、教师、学校、算法与平台之间谁能看、谁能改、谁能申诉、谁承担后果。
5. **隐私与同意：** 检查每类数据是否必要、自愿、可撤回、可纠错，尤其禁止用门禁、消费和夜间行为秘密推断学习或健康状态。
6. **社群动力：** 研究组队、导师、排行榜、反应表情、社区目标是否造成排斥、骚扰、搭便车或少数群体额外负担。
7. **可访问与包容：** 确保不用颜色、速度、手势、声音、英语梗或游戏经验作为进入核心功能的门槛。
8. **研究诚实：** 保存原始观察、反例、样本边界和未解决问题；小样本只支持设计发现，不声称统计代表性或学习效果。

任何承接者都不是独自决定产品伦理的“背锅位”，也不负责诊断学生、预测能力、裁定成绩或替学校作权威决定。没有独立人因队员时，出现高风险发现应由产品总集成人员先阻断合并，再邀请真实用户或适当专家复核；不能让 Codex 同时成为作者、证据来源和最终批准者。

## 3. 人因研究的八个固定维度

每一条游戏机制和每一个产品切片都必须回答下列问题：

| 维度 | 必答问题 | 典型证据 |
|---|---|---|
| 可理解性 | 第一次看到时，用户认为它是什么？会不会误解为正式成绩、医学结论或权威命令？ | 首读复述、术语卡片分类、错误解释原话 |
| 可行动性 | 用户能否说出下一步、后果、撤回和求助入口？ | 任务走查、无提示完成、错误恢复 |
| 情绪与压力 | 它是鼓励、提醒还是羞辱/催促？倒计时、连胜、稀缺是否制造不必要焦虑？ | 情绪词、压力评分、退出原因 |
| 公平与权力 | 谁受益、谁承担风险、谁没有发言权？是否把结构性问题写成个人失败？ | 利益相关者图、反事实场景、申诉走查 |
| 隐私与同意 | 数据是否必要、可选、可撤回、可更正？拒绝提供会不会损失基本权益？ | 数据旅程、同意复述、权限预览 |
| 社会互动 | 组队、导师、公开展示是否引发排斥、骚扰、搭便车、刷贡献或人气竞争？ | 情景访谈、小组观察、举报/退出演练 |
| 文化与语言 | 隐喻是否依赖篮球、音游、英语、华氏温标或特定校园文化？正式名称是否并列？ | 双语复述、跨专业/年级认知访谈 |
| 可访问性 | 键盘、触屏、读屏、减少动效、非颜色编码和低游戏经验路径是否信息等价？ | WCAG 走查、辅助技术/替代路径测试 |

## 6. Degree Fahrenheit 专项协议

### 6.1 产品定义

`Degree Fahrenheit · Academic Climate` 是一个**本人私密、主动开启、随时关闭的学业状态外观层**。它不是：

- 成绩、GPA、能力值、人格值、就业力或学校正式评价；
- 医学体温、健康诊断或心理状态推断；
- 越高越好的一条连续刻度；
- 教师、学校、家长、雇主或同伴可默认查看的指标。

原梗同时用了环境温度（60°F/70°F）和人体温度（98.6°F/100°F），所以不能把四个点连成一条科学量表。第一版只允许显示为四张**离散语义卡**或可选文案皮肤，并始终并列原始维度、时间范围、来源和“非医学/非成绩”说明。

### 6.2 可研究的评价因素

第一轮不得设置权重，也不得合成总分。候选输入仅用于显示多维状态：

| 因素 | 建议数据 | 人因问题 |
|---|---|---|
| 负荷—容量匹配 | 本人设定的可用时间与已承诺任务 | 系统是否把资源不足误写成个人不努力？ |
| 截止期限密度 | 未来 7/14 天任务聚集与冲突 | 倒计时是在帮助安排还是制造焦虑？ |
| 进度动量 | 本人与自己目标相比的近期完成/修订 | 会不会诱导刷时长、断签或过度学习？ |
| 任务清晰度 | 任务是否有要求、来源、Done 与下一步 | 模糊教学要求不能归罪给学生 |
| 时间表冲突 | 课程、工作、通勤、照护与活动的自愿输入 | 是否包容非传统学生和现实责任？ |
| 支持可得性 | Office Hours、同伴、导师、服务和人工通道 | “有资源”是否真的可达、可负担、无羞耻？ |
| 证据置信 | 数据新鲜度、缺口、冲突与本人纠错状态 | 是否诚实显示未知，而非伪精确？ |
| 恢复感受（可选敏感项） | 本人自报、短期、可删除 | 不从在线时段、门禁、消费或设备行为推断健康 |

明确禁止作为温度输入：GPA/班级排名、门禁轨迹、支付与消费、食堂选择、聊天内容、深夜在线、设备传感器、医疗或心理数据、同伴评价、人气和付费行为。

### 6.3 三个待测版本

1. **A · 原梗版：** 60°F/70°F/98.6°F/100°F 四张离散卡 + 原始维度 + 明确声明。
2. **B · 低误解版：** 只用“回暖中 / 室温 / 稳态 / 过热”文字与图形，不显示数字。
3. **C · 无隐喻对照：** 只显示负荷、期限、进度、清晰度、支持和未知项。

不得只测试 A。若用户更喜欢 A 但更容易误解，安全和可行动性优先于“好玩”。

### 6.4 研究问题与记录指标

对每位参与者先展示、后提问，禁止先解释梗：

1. “你觉得这是什么？谁算出来的？会影响什么？”
2. “98.6°F 和 100°F 哪个更好？为什么？”
3. “它是不是成绩、能力、医学体温或学校正式结论？”
4. “你下一步会做什么？从哪里看依据、修改数据或关闭它？”
5. “你愿意让谁看到？哪些数据绝不能参与计算？”
6. “这个表达让你觉得鼓励、平静、困惑、被评判还是焦虑？”

记录原话与原始人数，不用小样本百分比包装成科学验证。最低记录字段：首读含义、方向理解、下一步、压力感、信任、隐私边界、关闭偏好、异常/反例。

### 6.5 快速研究计划

- **样本：** 先做 6–10 名便利样本，主动覆盖不同年级、专业、游戏经验与语言背景；如能找到使用读屏、色觉差异或注意力/动效敏感的参与者，应单独记录需求。样本不代表全校。
- **方法：** 15–20 分钟认知访谈 + think-aloud；A/B/C 顺序轮换，避免固定顺序偏差。
- **隐私：** 不收姓名、学号、真实成绩、健康信息；使用 `P01` 等编号；录音前单独同意，不同意则只记笔记。
- **停损：** 任何版本出现重复的“官方分数/医学诊断/越高越好”误解、明显羞辱或无法关闭，应先改版，不带着解释硬过关。
- **采用门槛：** 参与者能在未被提示时说清“私密、可选、非成绩/非医学”，找到原始依据和退出入口，并能给出合理下一步；否则回退 B 或 C。

## 7. Human Factors Scouting Room 工作流

### 7.1 目标与边界

Scouting Room 把“产品负责人抛出功能，人因同学回答问题”改造成一条可复查的研究流水线。它的目标不是让人因同学替 AI 猜答案，而是：

1. AI 先完成资料检索、规格追溯和风险初筛；
2. 人因主责独立完成首读、选择研究方法并取得真实参与者证据；
3. 产品、模块 owner 与人因主责共同决定保留、修改、延后或停止；
4. 结论进入功能验收和 PR，而不是留在聊天里。

一张机制卡只处理一个明确问题。不能把“整个 F-006 好不好”作为一张卡，也不能让同学一次回答 139 个抽象问题。

### 7.2 三方责任边界

| 内容 | AI 可以先完成 | 人因主责必须完成 | 团队共同决定 |
|---|---|---|---|
| 官方事实、竞品机制、规则与研究来源 | 查找、引用、标版本和置信 | 检查这些材料是否忽略本地语境 | 是否足以支持当前产品决定 |
| F/X/EXP 与稳定功能追溯 | 找到现有归属、冲突和缺口 | 判断正式语义与用户理解是否一致 | 是否修改规格或保持实验状态 |
| 风险 | 根据清单提出伤害假设和反例 | 观察真实理解、情绪、权力与群体差异 | 接受、缓解、延后或拒绝风险 |
| 用户声音 | 生成不诱导的访谈草稿 | 招募、同意、访谈、观察、匿名记录 | 哪些发现进入验收与路线图 |
| 最终答案 | 只能给带来源的事实和明确标注的假设 | 不能仅凭个人意见替全体用户发言 | 产品 owner 负责范围，人因主责有权提出 Stop |

AI 能查到，不等于 AI 能替用户回答。凡是“这会不会羞辱人、是否感到公平、这个梗在本地是什么意思、谁会因此被排除”等问题，都必须保留为人因研究问题。

### 7.3 状态流

```text
INBOX
  → AI_PRE_AUDIT
  → BLIND_FIRST_READ
  → FIELD_MISSION
  → DECISION_REVIEW
  → BUILD_READY
  → IN_PRODUCT_RETEST
  → CLOSED
```

| 状态 | 进入条件 | 离开条件 |
|---|---|---|
| `INBOX` | 有功能说明、目标用户和正式行为 | 机制范围已缩成一张卡能回答的问题 |
| `AI_PRE_AUDIT` | AI 可读取规格和来源 | 已分开“已确认事实 / AI 假设 / 未知”，每个事实有来源 |
| `BLIND_FIRST_READ` | 有不带 AI 结论的原始说明或原型 | 人因主责提交自己的首读、担忧与研究建议 |
| `FIELD_MISSION` | 已选研究任务和最小参与者范围 | 有匿名证据、反例、样本局限和异常记录 |
| `DECISION_REVIEW` | 证据可由另一人复核 | 团队记录 `KEEP/REVISE/DEFER/STOP` 与理由 |
| `BUILD_READY` | 采用边界和人因验收条件已写入规格 | 模块 owner 将条件纳入实现与测试 |
| `IN_PRODUCT_RETEST` | 有真实可操作版本 | 同一风险在实现中复测，不能拿概念访谈代替 |
| `CLOSED` | 结论、证据、PR/规格和遗留风险已互相链接 | 只有新证据或版本变化才重新打开 |

未进入 `BUILD_READY` 的高风险机制不得因“视觉已经做了”而进入产品；概念测试通过也不等于实机测试通过。

### 7.4 机制侦察卡模板

每张卡使用以下最小合同。字段可放在 GitHub Issue、飞书任务或本地文档，但同一张卡只能有一个当前事实源。

```yaml
card_id: HF-CARD-###

formal_feature: "不使用游戏隐喻的正式功能名"

source_mechanism: "2K / maimai / 校园场景 / 原创"
problem_to_solve: "这张卡只解决什么问题"
affected_users: [student, teacher, institution]
authority_effect: "它会影响建议、排序、资格、支付、通行或仅影响外观？"
data_used: ["必要数据"]
data_forbidden: ["禁止推断或默认使用的数据"]

ai_confirmed:
  - claim: "可核验事实"
    source: "URL 或项目路径"
    confidence: high | medium | low
ai_hypotheses:
  - "明确写成假设，不冒充用户结论"

  - "首要未知"

blind_first_read:
  meaning: "人因主责第一眼认为它是什么"
  likely_winners_losers: "谁可能受益或受损"
  biggest_concern: "最担心的后果"
  disagreement_with_ai: "与 AI 假设不同之处"
```

### 7.5 防止 AI 锚定

一张卡分成两个可见层：

- **首读层：** 只展示功能说明、正式行为、用户、原型和必要上下文；不展示 AI 推荐答案。
- **研究层：** 首读提交后再展开 AI 已确认事实、风险假设和来源，允许人因主责反驳。

固定规则：

1. AI 不先写“用户应该会喜欢/理解”，只写可证伪假设。
2. 访谈先问“你觉得这是什么”，再解释设计意图；不能把正确答案塞进问题。
3. 选择题只用于快速分类，后面必须跟“为什么、发生了什么、有什么反例”。
4. 人因主责可以回复“问题本身有偏见/缺少关键群体”，不用在坏选项里强选。
5. AI 的高置信仅表示来源事实可靠，不表示产品价值判断正确。

### 7.6 六种研究任务

| 任务 | 适用问题 | 最小交付 | 不应声称 |
|---|---|---|---|
| `quick_scout` 快速侦察 | 低风险术语或一处交互 | 首读、最大风险、反例、下一步 | 代表真实用户验证 |
| `player_test` 玩家测试 | 用户能否看懂并完成任务 | 3–6 人 think-aloud、任务结果、错误恢复 | 统计代表性或学习效果 |
| `cultural_decode` 文化解码 | 温度、赛季、球探、Boss、英文梗 | 语义差异、替代词、需并列的正式名称 | 一个群体有唯一文化解释 |
| `power_map` 制度地图 | 成绩、机会、教师、学校、AI 权威 | 查看/修改/签发/申诉责任图与受影响群体 | 技术可以替代制度责任 |
| `pressure_test` 压力测试 | 排名、倒计时、连胜、稀缺、公开展示 | 焦虑/羞辱/FOMO 路径、退出和普通模式 | “游戏化天然提高积极性” |
| `accessibility_test` 可访问性测试 | 手势、颜色、动效、声音、密集 HUD | 键盘/触屏/读屏/减少动效等价性记录 | 有替代文字就等于完整可访问 |

高风险卡通常至少需要两种任务，例如 Degree Fahrenheit 使用 `cultural_decode + player_test + pressure_test`；门禁和支付使用 `power_map + player_test + accessibility_test`。

### 7.7 四态决策

| 决策 | 含义 | 最低证据 | 后续动作 |
|---|---|---|---|
| `KEEP` | 当前方向可继续，但仍受已写边界约束 | 没有未处理 Stop 风险；首读与行动路径基本一致 | 写入验收，进入 `BUILD_READY` |
| `REVISE` | 价值存在，但表达、数据、权限或退出需要修改 | 有明确问题和可测试修改方案 | 修改后回到 `BLIND_FIRST_READ` |
| `DEFER` | 证据、时间、样本或依赖不足 | 清楚写明缺什么，不能只写“以后再说” | 保持实验状态，不进入当前 Slice |
| `STOP` | 伤害不可接受，或必须依赖被禁止机制才能成立 | 具体伤害路径、受影响者和不可接受原因 | 从实现范围移除并记录安全替代 |

`KEEP` 不是“同学喜欢”，`STOP` 也不是个人否决。两者都必须留下证据、反例、局限和 reviewer；出现支付资格、秘密画像、公开羞辱、医学冒充或无申诉权威决定时，可先以 Stop 风险阻断合并，再由团队处理。

### 7.8 不枯燥的呈现语法

每张卡可以使用一层原创 Scouting Report 包装，但必须与正式字段并列：

| 游戏化标题 | 正式含义 |
|---|---|
| `Mechanic` | 机制/功能 |
| `Player Impact` | 受影响用户与后果 |
| `Fog of War` | 尚未验证的未知 |
| `Boss Risk` | 最大伤害路径 |
| `Counterplay` | 退出、撤回、申诉和替代方案 |
| `Evidence Replay` | 匿名原话、观察、反例与样本局限 |
| `Coach Decision` | KEEP / REVISE / DEFER / STOP |

游戏化只改善参与感，不能把真实焦虑、疾病、挂科或不公平做成笑料，也不能用积分、连签或排行榜考核研究同学。

### 7.9 工作节奏与优先级

- **主 WIP 仍为 1：** 同一时间只让一张高风险卡处于 `FIELD_MISSION`；其他卡可在 AI 预审或 Inbox 等待。
- **每日 Human Factors Clinic：** 20 分钟，最多快速处理三张卡；建议节奏为 3 分钟事实、5 分钟首读、7 分钟证据、3 分钟决定、2 分钟分配下一步。
- **先高风险后好玩：** 先审成绩/评分、机会匹配、门禁、支付、健康、人事和学校决策；再审排名/倒计时/社群；最后审纯装饰和文案。
- **风险排序不用伪精确总分：** 依次比较影响范围、后果严重度、可逆性、权力不对称和证据未知度，并写一句排序理由。
- **现场停损：** 如果研究会妨碍 P0，保留风险登记和安全默认，延后完整研究；不能反过来用赶工删除退出、申诉或隐私边界。

### 7.10 给 AI 的预审指令

把下面这段连同机制说明交给任意接手 AI：

```text
读取 product/HUMAN-FACTORS.md、对应模块 SPEC、product/BOUNDARIES.md，
为这个机制生成一张 HF-CARD 草稿。

你只能先完成：来源事实、F/X/EXP 追溯、数据/权威边界、可证伪风险假设。
把“已确认事实、AI 假设、必须由真实用户回答的问题”分开。
unknowns_for_human 最多三个；不要模拟参与者，不要替用户判断喜欢、公平或压力。
不要给 KEEP/STOP 最终结论，只建议最小 research mission。
如果缺少来源，写 unknown，不补造。
```

### 7.12 GitHub 接口（正式建仓后启用）

- 一张正在推进的功能 Issue 内包含一个人因工作包；只有涉及跨模块或 Stop 级风险时才拆独立 `HF-CARD` Issue，避免 Issue 爆炸。
- 建议标签：`hf/needs-first-read`、`hf/needs-evidence`、`hf/revise`、`hf/stop-risk`、`hf/build-ready`。
- Issue owner 是人因主责；产品总集成和模块 owner 为 reviewer。AI 不能成为唯一 owner 或 reviewer。
- PR 必须链接卡片决定和新增验收条件；若实现改变文案、数据、权限、公开范围或失败路径，卡片回到 `IN_PRODUCT_RETEST`。
- Git 仓只保存匿名研究摘要。真实姓名、学号、联系方式、原始录音和可识别截图不进入仓库；原始材料若确需保存，必须取得同意并使用受控位置和保留期。

### 7.13 完整示例：Degree Fahrenheit

```yaml
card_id: HF-CARD-001

maps_to: [F006-01, F006-05, F006-07, F006-10, F006-13, F006-14]
problem_to_solve: "温度隐喻能否帮助行动而不被理解成成绩或医学判断"

authority_effect: "只影响本人界面；不能影响成绩、资格、推荐或他人权限"
data_used: ["本人可用时间", "期限密度", "任务清晰度", "支持可得性", "证据新鲜度"]
data_forbidden: ["GPA/排名", "门禁", "消费", "夜间在线", "健康/心理数据", "人气"]

    source: "modules/06-performance-center/SPEC.md#4-degree-fahrenheit-实验"
    confidence: high
ai_hypotheses:
  - "部分用户可能把数字理解成百分制成绩"
  - "不熟悉华氏温标的用户可能只看到随机数字"
unknowns_for_human:
  - "第一次看到时，用户认为它是什么、由谁决定？"
  - "A 数字版、B 文字版、C 无隐喻版中，哪版最可理解且可行动？"
  - "哪些表达引发压力、被评判感或医学联想？"

mission: cultural_decode + player_test + pressure_test
decision: DEFER
decision_reason: "等待真实首读证据；不能凭团队喜欢这个梗直接进入实现"
owner: human_factors_research
reviewers: [product_integrator, performance_center_owner]
status: AI_PRE_AUDIT
```

这张示例卡的 `DEFER` 表示“等待证据”，不是否定创意；完成第 6 节的 A/B/C 访谈后，再根据证据改为 KEEP、REVISE 或 STOP。

### 7.14 课堂接梗回路 / Banter Relay

用户提供的课堂经历指向一个比“加更多梗”更重要的设计假设：高中课堂中，教师发出一句问题、一个动作或一个夸张说法，学生能立即接话、质疑、比划、重述并得到教师回应；大学内容更抽象后，这种反馈回路变弱。项目不把个人经历保存成画像，而把它抽象成可验证的交互模式：

```text
现象 / 问题 / 教师抛梗
  → 学生回应（选择、语音、草图、手势、反问）
  → 教师或 AI 明确接住
  → 追问、反例或可执行挑战
  → 正式定义 + 证据 + 适用边界
  → 保存为本人可控的记忆锚点
  → Replay 与下一步
```

#### 两条并行表达

每个幽默、直觉或身体化回应都要同时保留：

- **我的说法 / 直觉 / 梗：** 帮助本人记忆，可以编辑、删除和保持私密；
- **正式概念 / 证据 / 边界：** 来源可定位，明确教师审核状态，不能被梗替代。

例如“为什么不能这样解释？”是进入证据比较的 Challenge Call，不是把学生问题立即判成错误；古文、英语或物理的幽默重述可以成为记忆锚点，但发布给全班前要检查事实、语境、文化可理解性和教师权限。

#### 游戏手柄课堂回答

`Arena Response` 是非 P0 实验，不等于只把选择题映射到 A/B/C/D：

1. 手柄完成选择、置信度、提交与查看依据；长文本和开放问题仍使用语音/键盘/触控。
2. 抢答时反馈“已收到 / 轮到你”，不能公开最后一名、用反应速度推断能力或让无手柄者处于劣势。
3. 回答后必须出现“为什么、正式概念、证据、是否改变答案”，而不是只有胜负和分数。
4. 教师可暂停、改题、接受多个合理解释并标记未知；AI 只能接住和生成候选追问，不能冒充教师最终权威。
5. 键盘、触控、读屏和纸面/口头路径信息等价；触觉可关闭，设备标识和按键轨迹默认不上云。

#### 人因验收假设

- 3 秒内能说出当前问题，10 秒内能说出下一动作及后果。
- 首次有意义回应目标不超过 60 秒；点击装饰和被动播放不计入。
- 教学适合时，每个活动至少包含一次 constructive 或 interactive 行为；不为了指标强迫所有内容游戏化。
- 学生回应后界面立即承认输入，不出现“是不是系统没收到”的空白。
- 幽默表达旁边能一跳到正式概念、来源和教师审核状态。
- 学生可以私密、删除、纠正或不保存个人梗与直觉。
- 没有真实参与者研究前，只能说“依据 ICAP、主动学习、提取练习与具身学习形成设计假设”，不能声称提升成绩或记忆。

### 7.15 实验外设池 / Peripheral Lab（全部非 P0）

这些设备只有在强化同一教学闭环时才采用；“现场有硬件”本身不是价值。

| 设备 | 最有价值的演示 | 接入边界 | 当前决定 |
|---|---|---|---|
| 游戏手柄 | Arena Response、赛季导航、个人置信度与私密触觉确认 | controller-first 非 controller-only；不记录原始设备指纹 | **首选实验**，先做双实体手柄验证 |
| RealSense 深度相机 | 用身体/手势演示轨迹、向量、波形或空间结构；把物理直觉变成可回放草图 | 原始深度/彩色流默认本地即弃；不做人脸识别、考勤、情绪或注意力监控 | P2 身体化学习实验 |
| NFC 读卡器 | 轻触进入课程、领取虚构任务卡、打开本人可控档案 | UID 不是可信身份；生产身份需校方、FIDO/PKI/PC/SC 与最小权限设计 | P2 现场仪式；默认用虚构卡 |
| 接触式芯片/智能卡读卡器 | 对可信归档做持卡签名/解锁演示，表现“档案属于学生且可携带” | 不读取银行卡、校园生产卡或未知卡；私钥不导出，PIN 不记录 | P2 安全演示，须独立威胁模型 |
| 56K 调制解调器 | `Campus Time Machine`：拨号音 → 老教务系统 → Reverse 进入本地主权 AI；也可演示极低带宽回退 | 不接真实 PSTN/未知线路，不作为网络依赖；录音/模拟优先 | **开场彩蛋候选** |
| “RJ23”线缆 | 暂无可靠身份 | 56K modem 常见为 RJ-11C；RJ 名称常被误用，必须先拍端口、数触点、查设备手册和电压 | **隔离待识别**，禁止试插 |

一个可选、但不进入今晚主线的完整装置是：

```text
Tap（NFC/智能卡）
  → Dial（56K 拨号时代的旧教务）
  → Reverse（进入 Jiaowu2K26）
  → Move（RealSense 身体化演示）
  → Answer（手柄选择 + 置信度）
  → Evidence / Replay（正式概念、来源与本人档案）
```

它同时回应 `Reverse` 与 `8bit`，但只有在 90 秒 Demo 主闭环稳定、设备型号/驱动/许可明确、设置与拆除不超过独立预算时才进入。任何真实校园卡、支付卡、门禁卡、相机影像或电话线路都不用于黑客松演示。

### 7.16 产品总集成人员 × Codex 双轮共创协议

当前最有效的方式不是让产品总集成人员先填一份很长的问卷，也不是让 Codex 独自“模拟用户”。采用 **原型先行、盲用在前、问题在后、自由想法最后补充** 的顺序：

```text
Codex 做可丢弃小原型与无诱导任务
  → 产品总集成人员第一次盲用并边用边说
  → 记录行为、犹豫、误解和情绪原话
  → 回答 6 个固定短问题
  → 再补充个人设计思考和奇怪脑洞
  → Codex 区分事实 / 观察 / 假设 / 建议并修订
  → 产品总集成人员审核采用、改版、延后或停止
  → 关键结论再交给真实目标用户验证
```

#### 第一轮：产品负责人形成性试玩

产品总集成人员既是最终范围 owner，也是一个真实使用者，但**不是“大学生群体”的代表样本**。每个可见切片先完成一次 10～15 分钟形成性试玩：

1. 只说明目标任务，不先解释按钮、设计意图或 AI 的风险判断。
2. 允许自然使用手柄、键鼠或触屏；要求边用边说“我以为这是什么、我准备做什么、我担心什么”。
3. 先保存原始反应，再展示 AI 预审；避免用户为了迎合设计说明而修改第一印象。
4. 试玩后回答六个固定问题：
   - 你认为这是什么页面，它现在最希望你完成什么？
   - 你下一步会做什么？执行后发生了什么，是否符合预期？
   - 哪一处最像游戏、哪一处只是套皮？为什么？
   - 哪句话、分数、动画或比较让你感到压力、被评判或不可信？
   - 换成键盘、鼠标、触屏或无游戏经验模式，你能否找到信息等价的路径？
   - 你需要看到什么来源、权限、状态或回退，才愿意相信并继续？
5. 最后开放自由补充：个人故事、梗、动作直觉和“如果这样会不会更有意思”都可以提出；它们先登记为设计假设，不自动变成全体用户需求。

#### 第二轮：目标用户小样本

- 一般界面形成性测试先找 **3～5 名**目标角色，优先覆盖低游戏经验、仅键鼠、触屏和至少一种可访问性需求；它能发现高频问题，不能支持统计性效果宣称。
- Degree Fahrenheit、公开比较、压力、付费、门禁、支付和教师/学校权力等高风险机制，继续使用本章规定的 **6～10 名**认知访谈或相应专项方法。
- 真人证据必须记录招募范围、设备、情境、匿名原话、反例和局限；不能把朋友或便利样本写成“学生都喜欢”。

#### 一次试玩的最小记录

```yaml
session_id: HF-SESSION-###
prototype_commit: "<git sha 或明确的本地版本>"
participant_scope: "product_owner | student | faculty | institution"
input_path: "controller | keyboard | mouse | touch | assistive_technology"
viewport_and_device: "..."
task: "不给按钮提示的目标任务"
raw_observations: []
participant_quotes_anonymized: []
outcome: "completed | completed_with_help | failed | stopped"
friction_and_recovery: []
pressure_or_trust_signals: []
accessibility_limits: []
researcher_interpretation: []
decision: "ADOPT | MODIFY | HOLD | STOP"
needs_real_user_evidence: true
```

Codex 可以准备原型、任务、问题、录屏检查点和分析草案，也可以使用 Computer Use 发现机械性问题；Computer Use、自动化测试和 AI persona 都**不计作参与者证据**。产品总集成人员负责确认原始记录没有被 AI 改写，并决定下一版是否进入真实用户测试。

## 9. 研究记录与 PR 合同

每个发现使用以下最小字段，保存在 Issue/PR 或未来的人因登记表中：

```yaml
finding_id: HF-FIND-###
mechanism: "原机制名"
maps_to: [Fxxx-xx, X-xx]
research_question: "要验证什么"
participant_context: "只写与理解有关的最小背景，不写身份隐私"
evidence: "匿名原话、行为、截图或任务结果"
severity: low | medium | high | stop
counterexample: "反例或不同理解"
decision: keep | revise | defer | reject | needs_more_evidence
owner: human_factors_research
reviewers: [product_integrator, module_owner]
date: YYYY-MM-DD
```

进入 Demo/合并前，人因检查至少回答：

- [ ] 正式名称、来源、状态、后果与下一步不被游戏包装遮住。
- [ ] 默认不公开跨人排名，不生成永久身份标签。
- [ ] 没有付费资格、随机教育机会、断签惩罚或不可关闭 FOMO。
- [ ] 敏感数据是最小、自愿、可撤回、可纠错的，拒绝不损害基本权益。
- [ ] 错误、失败、离线、撤回、举报、申诉和人工接管可走通。
- [ ] 沉浸、轻量、传统、减少动效模式信息等价。
- [ ] 手柄、键盘、鼠标和触屏没有输入特权；焦点、状态、错误与恢复在设备切换后保持。
- [ ] 研究证据保留反例和局限，没有把便利样本写成“学生都喜欢”。
